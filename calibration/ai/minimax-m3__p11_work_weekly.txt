**本周工作周报**

**一、本周工作概述**

本周主要完成了核心交易接口的性能优化工作，并对一次线上接口超时故障进行了紧急排查与修复。同时，配合业务方完成了一个新接口的开发与联调，日常运维工作正常推进。

**二、接口性能优化**

本周重点针对订单查询接口（/api/order/list）进行了性能优化。该接口在大数据量分页查询场景下平均响应时间超过 800ms，偶发超过 2s，严重影响前端体验。

具体优化措施如下：

1. **慢 SQL 分析与索引优化**：通过 Arthas 抓取接口调用链路，结合慢查询日志定位到核心 SQL 存在全表扫描问题。原 SQL 中 `user_id` 字段未建索引，且 `created_at` 排序字段索引使用率低。新增联合索引 `idx_user_status_created(user_id, status, created_at)`，使查询从全表扫描降为索引扫描。

2. **引入 Redis 缓存**：针对热点用户的订单列表数据，引入 Redis 缓存，设置 5 分钟过期时间，并采用 Cache-Aside 模式。为防止缓存穿透，对不存在的用户 ID 返回空值并设置短过期时间。同时在数据更新时主动失效缓存，避免脏读。

3. **结果集压缩与字段精简**：后端响应体启用 Gzip 压缩，精简非必要字段，将列表返回字段从 18 个收敛至 10 个，下行数据量减少约 40%。

4. **异步化非关键逻辑**：将用户标签、推荐信息等非关键字段的下游调用改为异步填充，配合 CompletableFuture 实现并行查询。

优化完成后，压测数据显示 P99 响应时间从 2100ms 降至 320ms，平均响应时间稳定在 150ms 以内，缓存命中率达 78%。本周已上线灰度，运行稳定。

**三、线上故障处理**

本周三下午 14:25，监控告警显示支付回调接口（/api/payment/callback）出现大量超时，错误率短时间飙升至 15%。立即启动应急响应流程：

1. **故障定位**：查看日志发现回调处理线程池队列堆积，活跃线程数打满。进一步分析发现是上游支付渠道批量补单，单批次推送近 2000 笔历史订单，每笔回调触发订单状态更新、风控校验、消息推送等多个 RPC 调用，单笔耗时在异常情况下被拉长。

2. **紧急止血**：迅速将回调接口的 Tomcat 最大线程数从 200 临时调整至 400，并重启服务，使队列积压逐步消化。同时联系上游支付方暂停补单推送。

3. **根因分析**：经排查，根本原因为消息推送服务（MQ Producer）在该时段出现 GC 频繁，导致单次 RPC 调用耗时从 50ms 飙升至 1.2s，引发雪球效应。

4. **后续改进**：本周已完成以下整改——为 MQ Producer 配置独立的线程池隔离；为回调接口增加超时熔断与降级返回；针对批量回调场景增加批处理能力，单批次支持 500 笔并发处理。同时补齐了线程池队列长度、MQ 发送耗时等关键监控指标，并完善了告警阈值。

截至本周四上午，故障相关服务已全部恢复，业务指标正常，未出现二次异常。
